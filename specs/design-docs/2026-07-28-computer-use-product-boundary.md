# Computer Use 的产品边界：现在为什么薄，以及往哪走

## 起因

一个直接的质疑：

> 禁用外部渠道通过发送指令控制本机的话，那电脑控制是不是就失去意义了？如果我本地对话控制电脑和浏览器，用户直接用鼠标操作不就行了。

这个质疑成立。本文记录为什么成立、限制的真实理由是什么，以及价值应该往哪找——避免下次做阶段 3 时重新纠结一遍。

## 结论先行

**当前阶段电脑控制的价值确实薄，但问题不在「限制外部渠道」这个决定，而在于这个限制的理由被误当成了产品边界。**

## 限制的真实理由

两条规则常被混为一谈：

| 规则 | 真实理由 |
|---|---|
| 外部渠道不能控制本机 | **结构化审批闭环还没建**，不是「外部渠道不该做这事」 |
| 本地桌面主会话可以 | 人在现场，人本身就是审批 |

Slack/飞书来的一句话可能是任何人发的，也可能被 prompt injection 污染。在没有审批门的情况下，`browser` 或 `set_value` 一旦执行就是既成事实。所以现在挡掉是「**还没准备好**」，不是「永远不给」。

`specs/design-docs/2026-07-27-computer-browser-control.md` 把「结构化审批 UI + 不可伪造 desktop capability」列在发布阶段 3，正是这个意思。**当前的 channel 封锁是脚手架，不是终点。**

## 「人有鼠标为什么还要 agent」

四个答案，其中一个现在拿不到：

1. **价值不在替你点一下，在替你点两百下。** 单次点击人永远更快。但「把这 10 个页面的价格抄进表格」是 200 次点击加切窗口。agent 的价值是长序列吞吐，不是单个动作。

2. **Computer use 是「没有 API」的兜底。** 有 API 就该走 API。它存在的全部理由是只有 GUI 的系统——内部 OA、老财务软件、没有自动化接口的桌面应用。用户当然能手动做，问题是要花一小时。

3. **组合能力才是杠杆。** 单独的电脑控制没意思；「读飞书消息 → 提取数据 → 在没有 API 的内部系统录入 → 截图存档」这条链才有意思。

4. **定时/触发执行——当前拿不到。** 「每天早上把昨天数据从 X 系统导出」才是无人值守价值。但 cron 触发的是子会话，会被 `nexu-toolcall-guard` 的会话来源门拦掉。**这是当前限制下损失最大的一块。**

## 关键洞察：问题可能是「控制哪台机器」

TabbyApp 的手机 VLM 控制是有价值的（小红书批量发布、多设备任务）。它为什么成立？

**因为那台手机不是用户正在用的手机。** 它在设备农场里，用户不看着它。

同样的逻辑套到电脑：**电脑控制真正的价值场景，大概率不是控制用户面前这台，而是控制用户不在的那台**——闲置 Mac mini、VM、远程机器。面前这台的价值只剩「长序列我懒得做」。

这正好呼应 trycua/cua 的产品定位：它整个平台围绕 **Sandbox + Lume（macOS VM 管理）** 建，主战场是「agent 在专属虚拟机里干活」，而不是抢用户的鼠标。nexu 目前只用了它的 driver 层（见 `2026-07-28` 的统一改造）。

## 另一条独立的天花板：click 永远不可验证

与本文主题相关但独立的事实：**点击类动作在操作系统层面没有确定性后置条件**，任何 provider 都证明不了「这次点击达成了意图」。cua-driver 自己的 `click` 工具描述原文：

> A click is never driver-verifiable (no read-back) ... confirm the effect via screenshot.

所以 nexu 的完成证据门对点击类只能给 advisory（「已投递，未证实」）。这意味着**即使解锁了外部渠道和 cron，无人值守场景仍然缺少「确认做成了」的能力**——这对定时任务尤其致命，因为没人看着屏幕。

细节见 memory `peekaboo-no-action-verification` 与 `cua-macos-viability`。

## 建议

**短期**：接受当前形态就是「给会用的人的一个长序列工具」。Preview 徽章已按产品要求去掉，但心态上它仍是 preview——不要当主打功能推。

**决定性的下一步是审批闭环，不是更多驱动能力。** 审批做完，外部渠道和 cron 才能解锁，「飞书发一句话 → agent 在 OA 提交报销 → 关键动作弹审批」才成立。在那之前增加更多 computer use 能力是在加宽一条封着的路。

**中期需要决定「控制哪台机器」。** 如果转向 agent 专属 VM / 远程机器，cua 的 Sandbox + Lume 就从「我们没用的部分」变成主体，架构选型要重新算一次。

**无人值守场景需要先解决验证问题**，否则定时任务只能报告「已投递」，没人知道到底成没成。
